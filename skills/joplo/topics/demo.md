# Joplo playback and interaction: demo

The engine renders scripted state at step k, plus disposable local exploration. It schedules plugin presenters on one clock; component drawing and input details belong to installed plugins.

## Playback and free exploration
- The first picture-changing input while playing pauses and applies the same input. Matching the next script action advances once and stays stopped, including before a following system step. It behaves like manual pause followed by that input.
- Declared work.free reactions remain available in build/share and review publications after scope filtering. Verify a non-scripted action in the actual published site, then reset; local effects must disappear without changing timeline state.
- Arbitration: exact next action → reachable other scenario on the same stage (confirm first) → element onClick, declared free reaction or native local behavior → existing hint. Type, value, target and plugin payload all matter; a bare click cannot complete a typing action.
- Blank/noninteractive clicks only pause, with no local-change notice. Covers/transition cards remain inert. Hover never pauses; while paused it matches normally. Touch tap completing hover follows the click rule.
- Pointerdown pauses immediately and the same drag continues. A declared element drag owns its pointer before stage pan or plugin orbit: the source follows the pointer (also inside scaled pictures) and is transparent to hit tests while dragged. On release the engine picks the destination under the pointer, else the one the dragged element overlaps most, else the nearest within about 48 stage px; with none it snaps back and changes nothing. Esc, a cancelled pointer, a window blur or a hidden page also snap back; a second finger or pointer never takes over a drag in progress. Known limit (0.3.0): that 48 px is measured in the outer stage scale, not the scale of a picture plugin inside it, so the "nearby" tolerance is larger in a shrunk picture and smaller in a magnified one — make endpoints big enough and keep unrelated endpoints apart. The first wheel event pauses and scrolls; keep the burst/inertia in its scroll container before stage zoom.
- Playback controls stay outside stage input. Editing keys stay with a focused editable control. Plugin actions enter the same arbiter; never independently advance the timeline.
- Sequential playback is the default everywhere (board, published site, embed, render --chain): when a scenario finishes during playback, the next scenario starts at once — no countdown, no end card. The order follows from chains first (a chapter that continues another plays right after it, wherever it is declared), then declaration order. A from chapter continues in the same shot; a scenario marked flow('Slice title', { autoplay: false }) is skipped together with the chapters that continue it, and playing such a branch stops at its end. Pausing, exploring, a pending scenario switch or stepping manually never jumps ahead; the replay / next-case controls appear only when the whole sequence has finished. Declare scenarios in viewing order.
- Play, jump, scenario change and reset discard local effects. Screenshots, video, deep links and __JOPLO_STATE__ always read the timeline. Frozen in-flight previews must not paint over accepted local edits; preserve their original anchor for reset/resume.
- Use native controls from installed plugins and read their skills for supported edits. Give clickable elements onClick so they work after takeover; use work.free for other declared secondary reactions; keep lasting results in scripted effects. Test actual inputs, not only autoplay.

## Actions and the shared clock
- Scripted scroll is a timeline projection: returning to an earlier step, resetting, or switching scenarios on the same stage restores the initial scroll baseline and applies only the selected prefix. Test 0 → scrolled step → 0 and a scenario without scrolling. Pausing an in-flight scroll keeps its intermediate position; ordinary render frames must not reset it.
- .drag(target, destination) accepts an element id or stage pixel point; .scroll(target, destination) accepts an element id or content offset. Declare the correct source and endpoint.
- .hover(target, ms) expresses a dwell; .act(name, target, data) uses the enabled plugin's data-only contract. Read its installed skill for field types, ranges, matching tolerance and presentation duration.
- Engine frames expose clock time, speed, running/paused state and gesture progress. Presenters sample it; independent timers must not drive the timeline. Pausing freezes cursor, gestures, media, text and plugin animation together.
- Only per-frame presenters re-render on every clock frame; ordinary elements re-render when state, run/pause or speed changes. If playback still stutters, measure before changing the piece: open the scenario in a browser, press Play, and record requestAnimationFrame intervals (fps, median, frames over 50 ms) or a CPU profile for 10–15 s. Time in React rendering points at the engine or a presenter re-rendering too much; time in paint points at heavy filters, masks or blend modes. A slow step change in the board can come from development-mode React; check the built site before cutting elements.
- Inputs belonging to another scenario prompt before switching. The default actionEntry: 'before' enters immediately before the matching action, useful for guided practice. For direct manipulation such as a chapter scrubber, set flow('Slice title', { actionEntry: 'after' }) on the destination scenario: confirmation lands after the matched action exactly once, showing its scripted result and leaving subsequent steps pending. Cancel preserves exploration; confirm discards it. Before-action entry at step zero exposes the selected action without reopening the inert scenario cover; ordinary reset or chapter selection still shows the cover. This does not change autoplay, normal case selection or from continuity.

## A draggable chapter entry
Give the scrubber and all year/chapter endpoints stable ids on the same stage. Declare each destination with a distinct .drag('scrubber', 'chapter_target', …effects) action and actionEntry: 'after'. Endpoint labels may sit just above or below the scrubber's row: a release near a label (about 48 stage px) still resolves to it, and a release far from every label snaps back. Make each endpoint element big enough to aim at. The endpoint, not just the source, distinguishes destinations; different free reactions must not silently navigate. Keyboard activation of a declared drag source chooses a scripted destination, so also keep the player's chapter/case selector available when there are several destinations.

Start playback before testing stage gestures: covers and transition cards intentionally ignore them. Confirm a cross-scenario drag, verify the destination picture immediately, cancel another switch and verify edits remain, then reset/resume and compare with a pristine timeline frame. With from, an ordinary chapter selection at step zero can still show the preceding ending until the entry action plays; do not mistake that for an after-entry failure.

## Independent views and focus
- Each layer is an independent view tree, created with components from installed plugins. In an option with layers, the first declared layer is the default initial view; start chooses a route, not a layer. Use flow('Slice title', { layer }) to choose another declared view, and keep unrelated demonstrations in separate features/options. Layers share state; one layer may show a different role or device. Do not put independent views inside a scaled composite screenshot.
- layer(title, tree, { role?, icon?, viewport? }) declares a layer; icons use the engine's documented layer icon keys. The director follows action targets and explicit shot/cue targets. A system-only scenario stays in its initial layer unless an effect selects another.
- shot(ids...) frames targets; shot() returns to the whole current director layer. Use focus for spotlight/highlight/callout/numbered/redact and hold(seconds) for time to read.
- Start wide, focus only what explains a change, and return wide for the result. A drawing plugin may expose its own framing effect; read its skill instead of using host focus as a substitute.

## Captions and pace
- Caption tells what happened; explain tells why; narrate is spoken presentation. Keep captions short enough to fit (24 CJK characters is the hard guidance limit). Name roles and use narration only where it adds meaning.
- A step's hold controls dwell; narration may extend waiting. The engine estimates spoken time and sequences chapters. Keep a long story in smaller scenarios with from, retaining the previous final state.
- Transition cards mark a real opening/ending/time shift. Most information should change on the view, not arrive as a text deck. Read story and the installed visual plugins' recipes.
- Media is provided by an explicitly configured plugin. A viewer gesture unlocks sound; pause/resume/speed share the clock and narration ducks background audio. Static frames stay silent. Read the plugin skill for resources and production limits.
- Build validates explicit narration audio after selecting the publication scope and resolving prepared resources. AUDIO_ASSET_MISSING / AUDIO_ASSET_INVALID blocks publication before writing output when a selected speech clip has no prepared audio asset; prepare or repair it and rebuild. It never falls back to a voice provider or grants spending permission. An excluded work’s missing clip does not block the selected scope, and timing-only hold('audio', ref) may still use an estimate without a prepared clip.
- Audio resource failures are exposed by the playback host; video recording fails instead of silently delivering missing audio. MEDIA_DECODE_BUDGET warns when simultaneous resources exceed the shared PCM budget at 48 kHz; MEDIA_DECODE_HEADROOM warns about 96 kHz devices. Check can estimate from inspected durations, while build uses decoded metadata when available; unknown resources and other device rates still need playback verification. MEDIA_ENCODE_BUDGET separately checks the 4 MiB encoded-byte cache for prepared audio, including simultaneous retained resources. This is independent of the 32 MiB Float32 PCM cache and the local compiler artifact limit. A large PCM WAV can fail encoded admission even when decoded mono PCM fits; transcode to lossless FLAC or a smaller supported encoding. Check reads cached prepared byte/channel/region metadata without generating or spending; absent artifacts only permit duration/stereo estimates, so prepare local resources and check again. Runtime errors name the cache, requested/retained bytes and limit. Read the media plugin guide for concrete authoring remedies.
- Media continuity is engine behavior for every media plugin: a track keeps playing across steps on the engine clock (it only re-seeks on a jump, reset or non-relay chapter change); playing the same resource again continues it; playing a different one with fadeMs crossfades (old out, new in, no silence); a continuing chapter starts with the music its previous chapter ended with. Explicit marker seeks reposition that track (even at 0ms) and start its fade from the marker, while ordinary steps/relay chapters preserve its driver. Overlapping outgoing/incoming audio both count toward the decoded-memory budget until the actual engine-clock fade ends. The host then destroys the faded driver and releases its leases even during the same long step, while retaining a lightweight retirement marker so stale snapshots cannot resurrect it; explicit play or seek can rebuild it. Static warnings describe planned snapshot overlap, not observed audible state: real narration duration can move fade timing. They must not be suppressed merely because a later real-time render may finish the fade, and they are not a promise that long tracks fit; the host applies fade/volume/narration ducking once. Video chain export records that same mix; film strips skip audio.

## Make it play like a film, not slides (Required for video-like pieces)
Viewers call a piece "a slide deck" when pictures swap in one frame and then sit still. The static storyboard cannot show either problem, so it never proves the piece moves well.
- No hard cuts. Every chapter/era/scene seam needs a transition the viewer can follow: carry one object across (a match cut through the subject: push in until it fills the frame, swap the world behind it, pull back), morph a shared object, crossfade layers, or move the camera over the swap. One deliberate cut is a signature move; more than that is a deck. A scene change must not reset all visual context.
- No dead frames. Nothing on screen may be completely still for more than about 1.5 s; a still composition lasts at most about 3.5 s, and something changes at element level every 2–2.5 s. During reading holds keep a slow, eased camera drift with an end point (constant-speed motion reads as a screensaver). Use the installed visual plugin's drift and enter/exit transitions; read its recipes.
- Verify real layout after fonts and transforms, not only check: npx joplo render . --scenario-id film.open --out still.png --audit-layout --audit-content '[data-jid="frame"]' --audit-important '[data-jid="quote"]' --audit-safe-area '0,920,1920,160' --audit-exclude '[data-jid="stamp"]'. Areas use actual page CSS pixels relative to the export root, or a selector inside it; importance and intentional decoration are explicit, never guessed from text meaning. The sibling .layout.json reports Range text-line bounds, clipping/safe-area warnings, source/element/work/scenario/step and evidence. A static result is final-state only (atMs:null), not animation proof.
- For motion use --film --audit-layout (fresh run; --sample-ms at most 50). The audit consumes the same export clock and JPEG frames: post-commit, entry finish and plugin-declared camera/drift/waypoint deadlines are sampled within the report's sampleToleranceMs; intervening intervals are sampled with --audit-every-ms (20–1000, default 250). A later step may interrupt a motion phase. Inspect evidence before editing: overlap is a geometry heuristic warning, masks/rotation/nonrectangular clipping or hidden importance remain unknown, and unmeasured intervals can contain issues. --audit-layout supports static or film, not sheet/video/frames/resume. It never changes layout or generates paid narration/resources.
- One main motion per beat; most beats 2–3 s. hold(seconds) is the author's pacing: a step with hold no longer gets the 3 s reading floor (caption reading time per character and narration still extend it). A step takes its pre-commit lead plus its post-commit dwell (the larger of visual dwell and narration). hold(seconds) only sets post-commit dwell, so summing holds alone underestimates runtime. System steps default to a 0.9 s pre-commit lead; use work({ pace: { systemLead: 0 }, ... }) for narration-led films or a finite 0–30 seconds to choose it. The work setting applies to every system step, including continuing chapters, and preserves explicit timing in reduced-motion mode. Cards still commit directly; narration waits keep the engine clock (and therefore drift and transitions) running.
- Calibrated resource audio keeps its AudioRegion: playback, progress and measured duration use contentStartFrame/contentFrames, excluding probes, encoder delay and guards; native decoder trim mismatches fail explicitly. Recorded/offline narration retains the original file plus numeric AudioRegion so downstream mixing can select the same content. Live and recorded supplied narration share the media host's existing 4 MiB encoded and 32 MiB decoded-PCM budgets. Recording preparation retains only validated content/region facts, releases its measurement lease and reacquires a bounded lease for playback; abort, failure, cancellation and unmount release consumer leases immediately, and late results cannot play. On a budget error, shorten the simultaneous content or prepare a smaller supported encoding (preserving region metadata), rather than raising limits or synthesizing replacement TTS.
- Audio-led dwell: narrate('Words', { audio: asset('./take.wav') }), hold('voice', { pad: 0.4 }) waits for this step's selected narration/dialogue duration plus 0.4 seconds. hold('audio', asset('./cue.wav'), { pad: 0 }) uses another existing audio resource's duration without playing it. pad defaults to 0.45 seconds and accepts finite 0–30; it replaces the normal breath rather than adding a second breath. Explicit audio-led hold removes caption/explain reading floors; dwell is still the maximum of the audio duration plus pad, numeric hold, required camera/stream work and plugin effectHold. Pre-commit actions/systemLead remain separate. Numeric hold keeps its old meaning. Playback already waits for actual narration completion; this API reuses that wait, so a shorter clip is not extended by the narration's character estimate. Without a prepared matching clip, planning uses an estimate and check/outline label it estimated; it does not synthesize audio. Measured cached voice timing is bound to the selected clip/voice/content-language identity; changed text, voice or language must not reuse an old measured duration. Check again after preparing audio, then inspect outline and render --film --voice real before lining up other tracks.
- Anti-deck gate: before building, write one line per beat — the main moving object, its start → end state, and the verb (push, morph, rise, swap…). If most beats are only fades or panels appearing, redesign them. A contact sheet that reads like slide thumbnails fails.
- Chapters: use chapter() default continuation; sequential playback of a continuing chapter continues in the same shot (no countdown, no reset, music keeps playing). Bring the next chapter's music in on the beat before the visual swap (play the next score with fadeMs; the old track fades out under it — a J-cut). Play the same score again to keep it going. Stop music only at the real ending.
- Film sampling has a 50 ms default observation tolerance: identical source can cross a step/chapter boundary one sample apart; pixel equality across browsers is not guaranteed. It freezes the browser clock before loading, advances on a fixed 16 ms loading grid and waits for DOM commits to settle before each sample. Loading time does not become playback time. Repeat the same command when checking timing; compare scenario/position timelines separately from pixel differences (fonts, browser and platform can still affect rasterization).
- Required review: run npx joplo render <dir> --scenario-id <first chapter> --film --chain --out film.png and read every page (one per chapter; red = one-frame full-screen change, grey = nothing visible changed for ≥ 1.5 s). The CLI prints every CUT and STILL with time and step; film.json beside it has the largest adjacent-frame change around every step. Fix every CUT that is not a deliberate signature and every STILL, then film again. Also record --video (real time) and watch it once start to end. Cells are samples on the engine clock; check a suspicious moment with --frames <dir> at full size before changing code — fine textures (1-px checkers, hairlines) shimmer as moiré under zoom or drift and show up as cuts. The opposite also happens: in a product-recording piece the real change is a few characters, a caret or a timer, below the STILL threshold, so a typing sequence can be reported as one long STILL. Crop the changing area across consecutive --frames before adding motion only to satisfy the detector.
- Review as a picky viewer, not the author: list issues with time code, evidence (frame/metric), impact, severity (blocker / major / minor / note) and verdict (APPROVE / APPROVE_WITH_NOTES / REVISE). Check mechanics first (cuts, stills, overlaps, cropped text), then meaning, then taste; "not cinematic enough" without evidence is not a finding. Do at least two rounds of film → issues → fix, and finish one chapter seam to delivery quality before copying the technique to the others.
- Static frames (render, --sheet, thumbnails, deep links) show settled pictures: no drift, no half-finished transitions. That is deliberate and is why the film strip is the motion check.
- Boundary (D94): "like a video" is a quality bar, not a motion-graphics engine. Joplo's timeline is made of real, interactive states (steps), not frames. Reach the bar with the small set of glue tools above — transitions between states (enter/exit, match cuts), camera (framing, drift, safe area), media continuity, and the film/video review. There are no keyframe timelines, compositions, per-frame drawing APIs or particle effects; when a piece needs showy motion graphics, render that clip with another tool and embed it as an asset through a plugin. Ask of any new idea: does it describe how states change and are seen (fine), or how pixels are drawn over time (out of scope)?

## Authoring an exploration beside the film
- Share the same state patch between a scripted action and its free reaction; put camera, media and completion effects only in the scripted step. Do not filter an arbitrary effect array by hand: patch() itself returns an array of writes.
- A discrete draggable timeline can snap to named endpoint elements. Pair each endpoint with a labeled click alternative. This demonstrates declared choices, not a continuously calculated simulation.
- Test each interaction at two positions: immediately before its scripted action (it should advance once and stop), and somewhere it is only a free reaction (timeline state must stay unchanged). Then test reset, resumed playback, and a branch's Cancel/Confirm separately.

## Film framing and control space
A camera close-up must not enlarge or move the controls viewers need to pause, seek or recover. Either keep authored navigation outside the transforming picture (an independently sized visual region with the chapter selector, credits and drag affordance in the surrounding layout), or use the installed visual plugin's fixed screen layer for full-bleed chrome over the moving picture and give the camera a safe area so targeted framings avoid it. Read that plugin's recipes.

The host can draw an input/keyboard record after a type/press step, and toasts can move it upward. Reserve a clear band for those host overlays, then inspect the type step in both render --sheet and live playback. The step title occupies the upper-left corner and narration can cover the bottom of the stage; keep headings and live controls out of those regions. Verify with host overlays shown, not only a clean stage screenshot. Do not infer safety from the authored tree alone or hide host overlays with project CSS. A camera can intentionally crop contextual menus during a close-up; the current action and its result still need to be visible and reachable.

## Frames, deep links and verification
- outline lists scenario and step ids. Use those ids in render/export; a deep link chooses where viewing starts and is not an access boundary. render takes qualified ids: --scenario-id <feature>.<option>.<scenario> and --step-id '<feature>.<option>.<scenario>#<n>' (the NOT_FOUND message lists the available scenario ids).
- joplo render --scenario-id <id> --step-id <id> --out frame.png renders timeline state. --sheet --columns 3 renders every step with captions/narration (settled frames only). --film [--chain] [--every 250] samples real playback on the engine clock for motion review; --video records a webm. Both need the export component (npx joplo setup).
- Exporting a video to publish elsewhere: render --video [--chain] starts at the cover fading out (loading and audio preparation are not recorded). --width 1920 --height 1080 (or --width 1080 --height 1920) sets the video resolution: the stage keeps its own aspect, is scaled sharply and centered on the theme background, so portrait output suits phone pages. The audio track is the media plugins' music plus generated narration: --voice real (default) mixes the clips npx joplo voice made for the current voice and holds each step for the real audio; lines without a clip use estimated timing silently and the CLI lists them, so generate voice first and record again (browser speech is never captured). --clean (or --hide cover,cursor,title,subtitles) leaves out player chrome; --srt <file> writes the subtitles timed to the video for the platform's own captions. Watch the result once; trust the listed missing lines, not the absence of an error.
- Direct composition geometry: --viewport 720x1280 sets the logical stage used by layout, camera, screen overlays and hit areas; --width 1080 --height 1920 sets output pixels. --no-frame removes the device bezel. Without --viewport, existing page geometry and desktop/mobile defaults remain unchanged. Use the same geometry for screenshots, --sheet, --film and --video before comparing them. --crop '[data-jid="picture"]' or --crop 0,0,450,800 crops screenshots, sheets, film analysis and frame files; numeric coordinates are CSS pixels relative to the export canvas, and selectors must resolve to one visible rectangle entirely inside it. CUT/STILL fractions use the cropped image. A sampled crop must keep a fixed CSS width and height: changing dimensions raises a timestamped error rather than mixing incomparable pixel arrays; crop a stable outer frame when the subject moves. Video cropping uses logical geometry instead; --crop with --video is rejected.
- Sampled film/frame capture explicitly sets frame.sampling. The host waits for current-frame async presentation tasks and React commits before reading pixels; it uses wall-clock deadlines without moving the frozen engine clock. Decode/task failures stop the export with the sample timestamp. Real-time --video uses normal playback, not this per-frame handshake; inspect that recording separately.
- Public offline frames: npx joplo render <dir> --scenario-id <first> --chain --frames-out output/frames --fps 30 --viewport 720x1280 --no-frame exports JPEG files named by engine milliseconds and timeline.json. The supported library entry is renderFrames from @joplo-app/server; do not import dist/dev.js, private routes or __JOPLO_RECORD__. Targets use round(frameIndex * 1000 / fps), not repeated fractional runFor calls. Frames use cached clip durations silently and never call paid TTS; absent clips use estimated timing. Clean frames omit cover/cursor/title/subtitles by default. This is sampled replay with a 50 ms observation tolerance, not a promise of byte-identical scheduling or font rasterization.
- --timeline output/timeline.json accompanies --film and --video too. Schema version 1 includes actual observed step commits/ends, chapter boundaries, generic media snapshots and committed play/seek/stop/volume changes, camera cues and narration events (text, cached clip id/file/duration when present). engineMs is engine time; outputMs is recording/frame time. Narration endAt is observed relative to playback start and outputEndMs is already aligned to the output; do not infer a clip's start from stepPlan. Film defaults to estimated narration, while frames and video default to cached real duration; choose the matching path when aligning alternate audio or subtitles. Continuing chapters retain the whole-chain clock; completion explicitly names the final scenario and actual engine/output end time. Referenced cached narration and media bytes are copied beside the timeline into <name>.assets/; file paths are relative to the JSON and remain usable after the temporary server closes. Media assets include audioInfo when the compiler measured an AudioRegion: sourceSampleRate, contentStartFrame, contentFrames and cycleFrames describe decoded samples, not encoded bytes. Rescale those frame counts to the decoder sample rate, trim to the content start and loop only cycleFrames; starting an encoded file at byte/sample zero can expose encoder delay, calibration audio or guard padding. Asset failures are explicit errors; no TTS is generated.
- WebM needs only the export component. An output ending in .mp4 additionally uses local ffmpeg with H.264/AAC; missing ffmpeg or encoding failure is an explicit error. Encoding writes a private temporary file and commits only a complete result; failure preserves an existing output. Audio assets are content-validated and atomically written; use --overwrite to repair a corrupt cached export asset. --voice estimate is silent estimated narration and --voice off skips narration; background media remains independent. --silent omits every audio track while keeping cached narration timing. Video results expose measured calibration offset and audio/video end points. Review a decoded audio signal against early and late narration events before accepting a long alternate mix; calibration offsets are not proof every external encoder preserves sync.
- Film cost: --every changes saved cells only; --sample-ms changes image-analysis frequency (20–250 ms, default 50). Use 100–250 ms for a fast exploratory pass, then 50 ms for final CUT/STILL review: brief transitions can fall between coarse samples. The JSON includes wall time, baseline/end RSS, a 5-second RSS trace and process-lifetime peak RSS (Node only, not Chromium). Compare speed at the same sample interval, geometry and quality; coarse-mode wall times do not establish an equivalent-quality speedup, and concurrent load affects measurements. --checkpoint output/checkpoint.json commits progress at chapter boundaries; --resume replays the engine to restore state while reusing verified pixel analysis. Content hashes include project source/CSS/assets, voice cache bytes plus prepared clip duration/voice identity, host and enabled plugin runtime/build identities, browser/platform and every rendering option. Changes invalidate the checkpoint. Resume validates identical step identities and commit offsets within 50 ms, requires the same stable scenario/step/active state and recomputes the short chapter seam; larger divergence asks for a fresh render; never substitute an initial chapter state. --chapter-timeout 180000 limits wall processing per chapter and preserves the last committed checkpoint on failure. Keep output paths separate when running concurrent exports.
- A full-size render can pass while a shorter board clips the input area. Check the actual visible hitbox with real pointer input in the board and the built site; DOM text existing is not proof it can be used.
- Fixed --width/--height dimensions are a capture size; --viewport explicitly overrides the logical page/layer geometry for export. In a browser wait for fonts and [data-jcamera][data-camera-settled="1"] plus two animation frames. Do not mistake DOM progress for painted pixels.
- Test first input, drag, wheel, hover, keyboard, confirmation cancel/confirm, reset and resumed playback. Compare restored frames and direct jumps with pristine script frames. Explain unverified devices or audio behavior.
- For layout, visual motion, shapes, charts and component APIs use the installed plugin skills. The engine has no built-in component vocabulary.

## Write a theme
A project theme is themes/<name>.css selected by config({ theme: '<name>' }). Define --jp-bg, --jp-ink, --jp-surface and --jp-font; set --jp-stroke: clean for ordinary CSS borders (omitting it inherits hand-drawn strokes). Scope ordinary selectors to an authored root class so third-party libraries do not recolor the player. Include required font bytes as data URLs or use an already installed platform font; remote CSS/font URLs are not an offline asset pipeline. Verify computed styles in the board and in the built site (npx joplo preview). Component defaults and styling recipes belong to the owning plugin.

## Branches, annotations and appearance
- fork(label, scenarioKey) adds a labeled route to another scenario; it does not silently branch automatic playback. Feature diffs report action-entry and autoplay policy changes separately, even when their static pictures are identical. Mark the optional destination flow with autoplay:false so sequential playback skips it; fork alone is a navigation choice, not an autoplay exclusion. Return links to main chapters must not mark those chapters optional.
- Keep fork labels short and verify the last choice at the actual viewport width: the strip scrolls horizontally when crowded. Avoid hiding an important return path in unnoticeable overflow. A film can end on its final visible state without a done badge when that badge crowds the choices.
- mark(id, text?, opts?) is an annotation anchored to a stable element. Empty labels are omitted; targets are still validated. Use --jp-annot for annotation color in a theme.
- .press('⌘K', ...effects) models a targetless keyboard step; keep editing keys inside editable elements. Keys and ids are not translated.
- Appearance changes host theme/font/stroke, not state. Follow director keeps framing in sync; a manually selected layer uses that layer until the viewer follows again.
- Custom themes live in themes/<name>.css and define --jp-* tokens; do not change authored data to recolor a view. For component-specific layout, motion and visual variables, read its installed plugin skill.
