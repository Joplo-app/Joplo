# 用 Joplo 设计 Joplo

这是 Joplo 自己持续维护的产品设计项目。我们用同一套 Feature / Option / Scenario 设计自己的产品，也把可追溯的过程留给用户观看：当时遇到什么问题、考虑过什么方案、怎样操作原型、做了什么取舍，以及后来又改了什么。

它收敛了原先分散的五个 `joplo-*` 项目。原有九个 Feature 的 14 套方案、65 条场景保持稳定 ID；最早的工作台、创作模型和 PR 功能差异补成独立 Feature。`invite`、`camping`、`agent-arch` 是不同业务的独立示例，`_v1` 是保留的历史归档。

## 打开这个设计项目

从仓库根目录运行（使用工作区源码，不需要等待 npm 发布新功能）：

```sh
pnpm install
pnpm joplo check examples/joplo
pnpm joplo dev examples/joplo --open
```

在看板中选择一个 Feature：先看其「设计回放／设计演进」，再进入具体交互。切换备选方案，可以比较当时保留的其他做法。这里的输入、终端、邀请、反馈和 PR 都由场景驱动，不会真正发送邀请、发布分享或创建评审。

## 准备给观众看的静态版本

```sh
pnpm joplo build examples/joplo --out scratch/joplo-design-site
```

每个 Feature 都有一个公开选择。原有九个 Feature 的 `design_journey` 复用真实代表场景，只增加开场和收尾，原场景保持不变。新补的历史工作台和创作模型在选定方案里显式展示设计演进，因此观众也能看到未选方向的取舍。

普通 build 只保留选定方案，规则、问题、私有评审信息等创作字段仍会被剥离。公开叙述只来自主动整理的画面和字幕，不依赖私有 review manifest。完整备选留在本地看板和源文件中。此命令只构建本地目录，不上传；分享或部署需要另行授权。

## 下一次怎样继续设计

1. 在同一个 `features/<id>/` 中增加方案或场景，保留既有 ID 与已有步骤身份。
2. 将真实用户目标、待决问题和已有证据分开；没有的历史不要补造成反馈或确认。
3. 用可操作画面表达差异。成功和失败都要有结果；没有建模的行为明确标注。
4. 先回放、截图和评审，再依据实际结论更新选择及公开设计记录。
5. 更新证据目录、相关文档与官方技能；不再另开一个平行 `joplo-<feature>` 项目。

新合入源码不自动等于 npm 已发行；尤其 `feature_diff` 的演示是设计回放，不证明生产 PR 评论生命周期已经验收。当前版本边界见[功能差异说明](../../docs/feature-diff/README.md)。
